# Журнал выводов

Что понял на каждом этапе и что сделал бы иначе. Оригинал для сравнения — `vladilenm/modern-second-brain`.

## Этап 0–1. Нить: сессии Claude Code → SQLite → поиск → MCP

**Что сделано.** `brain sync` читает `~/.claude/projects/*/*.jsonl`, `brain search` ищет через FTS5,
`brain mcp` отдаёт Claude два инструмента: `search` и `get_record`.

**Формат сессий Claude Code.**
- Одна строка — одно событие. Типов много (`attachment`, `system`, `queue-operation`, `cost-state`…),
  разговор — только `user` и `assistant`.
- `content` бывает строкой или списком блоков. Нужны блоки `text`; `thinking` — рассуждения модели,
  `tool_use`/`tool_result` — работа инструментов. Реплика `user`, где только `tool_result`, — не слова человека.
- Подагенты лежат в `<session>/subagents/` — побочные ветки.

**Находки на реальных данных (в тестах на выдуманных их бы не было):**
1. *Одна сессия — несколько файлов.* Если в разговоре меняется рабочая папка, Claude Code продолжает
   ту же сессию (тот же id) в папке нового проекта. Ключ по имени файла давал коллизию: второй файл
   молча перезаписывал первый. Решение: группировать файлы по id сессии.
2. *Продолжение копирует историю.* Новый файл начинается с полной копии прежних событий (те же `uuid`,
   но другой `cwd`). Без дедупликации разговор попадал в базу дважды. Решение: склеивать файлы
   от старого к новому и выкидывать повторы по `uuid`.

**MCP SDK.** Протокол берёт на себя `@modelcontextprotocol/sdk`: `server.registerTool(имя, {description,
inputSchema}, обработчик)`, схема параметров — zod-объект, SDK превращает его в JSON Schema.
У автора протокол написан руками (~150 строк). stdout занят протоколом — логировать только в stderr.

**Отличия от оригинала, которые стоит разобрать дальше:**
- Токенизатор: у нас стандартный `unicode61` (целые слова), у автора `trigram` (подстроки) —
  «клуб» находит «клуба». Для русского это важно → этап 2.
- Синхронизация перечитывает всё каждый раз. У автора — только изменившиеся файлы и после
  30 минут тишины → этап 4.
- Ранжирование — голый bm25 без весов полей и свежести → этап 2.
- Заголовок сессии иногда начинается со служебной вставки (`<browser_instruction>…`, `<ide_…>`) —
  это тоже реплика `user`. Стоит вырезать такие теги из текста.

## Переезд на TypeScript

Python-версия переписана на TS один к одному, чтобы было проще читать. Что выяснилось по дороге:
- *SQLite с FTS5 в Node.* Встроенный `node:sqlite` в Node 22.11 собран без FTS5 (`no such module: fts5`),
  в Node 26 — уже с ним. На 22.11 пробовал `better-sqlite3`: v13 (бинарники внутри пакета) падала
  с segfault, v12 работала. Перешёл на Node 26 (`.nvmrc`) и встроенный модуль — нативных зависимостей нет.
  Вернуться к `better-sqlite3` можно, если понадобится скорость или удобства (типизированные строки, `transaction()`).
- *Транзакции.* Python-модуль `sqlite3` сам открывает транзакцию, а `node:sqlite` коммитит каждый
  запрос. Поэтому есть свой `transaction()` на `SAVEPOINT`: его можно вкладывать — `upsert` атомарен сам
  по себе, а `sync` оборачивает весь проход в одну внешнюю транзакцию. Соединение закрываем явно: `conn.close()`.
- *Типы строк.* `node:sqlite` возвращает `Record<string, SQLOutputValue>` — о наших колонках он не знает,
  тип строки приходится задавать вручную (`as unknown as SearchHit[]`).
- *Запуск без сборки.* `tsx` выполняет `.ts` напрямую, импорты пишутся с расширением `.ts`
  (`allowImportingTsExtensions`). Тесты — встроенный `node:test`.
- *Мелочи, которые в Python были бесплатными:* срез строки `[:100]` режет по символам, а в JS
  `slice` — по UTF-16 (эмодзи ломается пополам), поэтому `Array.from(s).slice(0, 100)`;
  `sort()` строк в JS без компаратора тоже по UTF-16 — для ISO-дат одинаково.
